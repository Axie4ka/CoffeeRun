# RepeatOrderUseCase: повтор по свежему меню

Согласован следующий этап после PlaceOrderUseCase. Один сценарий для списка и деталей, без изменения исторического заказа и без нового сервера.

## Решение

- MenuRepository.refresh(): MenuSnapshot возвращает товары и цены одного свежего ответа. NetworkMenuRepository обновляет общий кеш только после успешной загрузки, под существующим Mutex; ошибка refresh не заменяется старым кешем.
- RepeatOrderUseCase(menu, cart, sessions) получает снимок, проверяет ID и точные опции, рассчитывает Product.unitPrice по текущим ценам и добавляет допустимые строки под проверкой исходной сессии. Перед изменением корзины проверяется cancellation. История не меняется.
- Нет молчаливой замены размера, молока, добавки, льда или примечания. Недоступная конфигурация пропускается целиком; отсутствие обязательных исторических опций не заполняется догадкой. Количество вне лимитов и невозможность добавить полное количество пропускаются с причиной.
- Domain RepeatOrderResult различает Added(число строк, пропуски, изменились ли цены), Unavailable(пропуски), NetworkError. Для пропуска хранится productId и причина. UI преобразует результат в существующий OrderRepeatResult с локализованным сообщением, без R.string в domain.
- Два ViewModel получают один use case из AppContainer; локальная защита повторного нажатия сохраняется. Прежняя функция repeatOrder из UI удаляется.
- Исправление равенства корзины B10, независимость истории от меню B08 и проверка цен на сервере остаются отдельно. Не добавляются библиотеки, очередь или новая схема БД.

## Проверка

Явный refresh после кеша, единый ответ товаров/опций, ошибка без stale fallback. Повтор по новой цене без изменения истории; исчезнувшие товар/размер/молоко/добавка/настройки/недопустимое количество; сохранение существующей корзины; тайм-аут/отмена/смена сессии. Два экрана дают одинаковые результаты. Unit-suite, APK, UI и независимое ревью.
