## 2. Исходное состояние перед исправлениями

Приложение использует Kotlin, Jetpack Compose, ViewModel, Flow/StateFlow, Navigation Compose, Retrofit, OkHttp, kotlinx.serialization, Coil и ручную передачу зависимостей через `AppContainer`. Токен сохраняется через DataStore. Корзина и выбранная кофейня — в памяти процесса.

Уже реализованы каталог и поиск, настройки напитка, корзина, выбор кофейни в том числе при оформлении, вход и регистрация, профиль и его редактирование, избранное, оформление, история и детали заказа, отмена заказа. Есть обновление заказов свайпом. Эти возможности нужно сохранять при изменениях.

## 3. Ошибки и риски корректности

### B01. Запоздавшие ответы предыдущей сессии — P1

- [x] Ввести общий контекст сессии с изменяющейся версией, привязать к нему персональные операции и проверять версию при применении результата.

**Проблема.** Загрузка, начатая до выхода, может завершиться позже и обновить данные. Одного `Boolean isLoggedIn` недостаточно для различения двух авторизованных сессий. Обычный `collect`, ожидающий `refresh()`, также задерживает обработку выхода.

**Изменение.** При выходе и новом входе менять `generation`, отменять старые операции, очищать персональные хранилища и ожидающие изменения. Проверка версии и запись результата должны быть согласованы атомарно: отдельная проверка перед несогласованной записью оставляет гонку. `collectLatest` полезен для наблюдателя, но сам по себе не защищает запросы, запущенные другими путями. Стабильный `userId` добавлять, когда его предоставляет сервер; локальная версия сессии полезна уже сейчас.

**Выполнено для заказов, избранного и профиля:** общий контекст, проверка результата и HTTP-запроса, отмена старых операций и очистка персонального состояния. Старый ответ, включая 404/401, не меняет данные нового входа. Повторный вход с одинаковой строкой токена различается по версии. Отмена сохранения профиля не показывает успех и снимает busy. Выход очищает корзину даже при закрытой Activity; восстановленная навигация проверяет владельца сессии.

**Готово, когда:** задержанный ответ пользователя A не меняет данные после выхода или входа B; это проверено для заказов, избранного и профиля. Старый 401 не очищает новый токен. Существующее поведение `TokenStore.clearIfStill(token)` сохранено.

### B02. Конкурентные изменения избранного — P1

- [x] Разделить подтверждённые данные и ожидающие действия; добавить единый координатор избранного.

**Проблема.** Действие выбирается до блокировки; откат старой ошибки может отменить более новое желание. `refresh()` способен перезаписать оптимистический результат. Отмена `viewModelScope` может прервать запрос после изменения сердечка.

**Изменение.** Хранить желаемое `true/false` по каждому товару и версии намерений. Репозиторий предоставляет явную установку состояния. Координатор согласует отправку, обновление, ошибки и смену сессии. Подробная схема — A03.

**Готово, когда:** серии «добавить → убрать → добавить» дают последнее желаемое состояние; действия над разными товарами не теряются; ошибка старого запроса не отменяет новое действие; обновление не стирает ожидающие изменения. Закрытие экрана и выход из аккаунта имеют разное, определённое поведение.

**Первоначально выполнено в NetworkFavoritesRepository; теперь механизм выделен в FavoritesCoordinator:** подтверждённое состояние, карта версий намерений и последовательная отправка в scope приложения. UI сохраняет toggle; внутри фиксируется явное желаемое значение. Актуальная ошибка откатывает только своё последнее намерение, старая не показывает неактуальное сообщение. При неизвестном сетевом исходе возможны временные расхождения с сервером; строгая гарантия после тайм-аута требует серверного механизма, как описано в A03.

### B03. Конфликт обновления, оформления и отмены заказа — P1

- [x] Организовать согласованное применение результатов всех операций с заказами.

**Проблема.** Старый ответ списка может затереть новый заказ или вернуть отменённому старый статус. Проверка `loading.isLocked` перед `withLock` не является атомарным объединением запросов.

**Изменение.** Хранить заказы по номеру и выполнять вставку/обновление через общий механизм. На первом этапе допустима последовательная обработка конфликтующих операций; другой вариант — версии и отбрасывание устаревших ответов. Для объединения одинаковых загрузок использовать общий выполняющийся `Deferred` с определённым владельцем и временем жизни. Отмена одного ожидающего экрана не должна неожиданно отменять загрузку для остальных.

**Готово, когда:** задержанный список не возвращает старый статус после отмены и не удаляет только что созданный заказ; одновременные потребители одной загрузки получают один результат или одну ошибку без лишних запросов.

**Выполнено:** выбран согласованный с пользователем вариант последовательной обработки в пределах одного входа, включая load и обновление после 409. ## 4. Изменения архитектуры

Цель — понятное владение данными и правилами при сохранении Compose, ViewModel и репозиториев. Для текущего размера приложения достаточно пакетов одного модуля.

```text
Compose → ViewModel → Use case / координатор → Repository → API / локальное хранилище
               ↘ простое наблюдение за данными ↗

Repository / координатор → Flow состояния → ViewModel → UiState → Compose
```

Use case — законченный сценарий пользователя. Координатор — объект, согласующий пересекающиеся действия во времени. Репозиторий — владелец данных и их согласованного обновления. Мьютекс и канал — инструменты реализации, а не самостоятельные архитектурные слои.

### A03. Общий координатор избранного — P1

- [x] Организовать общую координацию избранного на приложение с привязкой операций к текущей сессии.

**Реализованный вариант после выделения:** общий FavoritesCoordinator реализует контракт Favorites для UI, хранит карту намерений и версии, согласует операции через Mutex. NetworkFavoritesRepository предоставляет confirmedIds, refresh(session), setFavorite(productId, selected, session) и clear(session), проверяя владельца перед записью. Подтверждённые ID и оптимистическое состояние разделены; публичный toggle сохранён в UI-контракте. Новых библиотек нет. Схема Channel ниже остаётся альтернативой реализации, а серверные гарантии после тайм-аута — отдельной задачей.

Предлагаемая модель:

1. Репозиторий хранит подтверждённые ID и предоставляет `setFavorite(productId, value)`.
2. Координатор хранит последнее желаемое состояние по каждому `productId`, версии намерений и выполняющиеся операции.
3. Отображаемое избранное получается из подтверждённых данных с наложенными ожидающими изменениями. Все экраны читают этот общий результат.
4. Нажатие атомарно обновляет желаемое состояние и отправляет сигнал в `Channel<Unit>(Channel.CONFLATED)`.
5. Единственный обработчик последовательно синхронизирует неподтверждённые значения, после каждого ответа вновь проверяя актуальные намерения. Карта ожидающих изменений, а не число сигналов, определяет оставшуюся работу.
6. Успех подтверждает отправленное значение для своей сессии; более новое намерение остаётся ожидающим. Старая ошибка не откатывает новую версию. Обновление с сервера проходит через те же правила и не стирает наложенные изменения.
7. Определить поведение актуальной ошибки: при однозначном отказе — откат соответствующего намерения и сообщение; при неизвестном сетевом исходе — согласование с сервером либо ограниченный повтор явной установки состояния. Бесконечного скрытого цикла повторов нет.
8. При смене сессии отменяются старые операции и очищаются ожидающие изменения. Поздние ответы не применяются.

`Channel.CONFLATED` хранит последнее ожидающее значение и отбрасывает предыдущие. Поэтому один канал команд по всем товарам терял бы действия: его здесь предлагается использовать только как сигнал к проверке карты. Передавать теряемые команды `toggle` нельзя. [Семантика conflation в документации Kotlin](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.channels/-channel/-factory/-c-o-n-f-l-a-t-e-d.html).

Уже отправленный запрос не стоит считать отменённым на сервере только потому, что клиент перестал его ждать. Для небольшого приложения последовательный обработчик проще; независимая параллельность по товарам — возможное дальнейшее улучшение.

**Граница гарантии:** после тайм-аута старый запрос может ещё выполняться на сервере и завершиться после нового. Клиентский канал и идемпотентность отдельного PUT/DELETE сами по себе не гарантируют порядок применения разных намерений. Для строгой гарантии последнего значения нужен согласованный серверный механизм версий/упорядочивания; без него требуется повторная сверка и синхронизация, а временное расхождение нужно учитывать в поведении и проверках.

**Готово, когда:** выполнены сценарии B02, а чтение/изменение карты, версий и подтверждённого состояния имеет единый порядок. Канал не используется для потери команд оформления заказов.

### A04. Сессия и время жизни операций — P1

### A08. Когда нужны более сложные элементы — P3

| Элемент | Когда добавлять |
|---|---|
| Reducer / MVI | Много связанных переходов состояния экрана, которые трудно проверять обычными методами |
| Конечный автомат | Авторизация, оформление или оплата требуют явно запрещать недопустимые переходы |
| Room как источник чтения | Нужны структурированные сохраняемые данные и работа без сети |
| Outbox + WorkManager | Нужно сохранять ожидающие действия и продолжать их после завершения процесса |
| Sync engine | Есть реальные конфликты между локальными и серверными изменениями |
| Модули `feature` / `core` | Нужны границы зависимостей, независимая работа и управление сборками |

Это варианты развития, а не список обязательных классов для CoffeeRun. Очередь в памяти не заменяет сохраняемую очередь; фоновое возобновление требует отдельного проектирования.

## 5. Функционал и пользовательский опыт

### F01. Сохранение корзины и кофейни — P1

- [ ] Сохранять корзину и выбранную кофейню; определить поведение при выходе и смене аккаунта.

Для небольшого выбора кофейни достаточно DataStore. Для корзины использовать Room в рамках обязательной ЛР6. Сохранять стабильные ID, конфигурации и количества; восстановленные цены/наличие перепроверять перед покупкой. Предусмотреть версию схемы и её миграции.

**Готово, когда:** после завершения процесса корзина и кофейня восстанавливаются; изменение каталога не приводит к покупке по неподтверждённой старой цене; выбранная политика аккаунтов не смешивает данные пользователей.

### F02. Редактирование позиции корзины — P2

- [ ] Открывать текущую конфигурацию строки, менять размер, молоко, добавки и примечание, сохранять изменение обратно.

**Готово, когда:** редактирование не добавляет случайную новую строку; цена пересчитывается; совпадение с другой конфигурацией объединяется по согласованным правилам B10; отмена редактирования ничего не меняет.

### F03. Автообновление активного заказа — P1

- [ ] Обновлять статус при открытии/возвращении на экран и периодически, пока активный заказ виден.

Начальный интервал можно выбрать около 30 секунд и уточнить по ограничениям сервера. Остановить опрос при закрытии экрана, уходе в фон, выходе и конечном статусе. Не создавать несколько независимых циклов для одного заказа. При ошибке оставить последний статус и обозначить, что он может быть устаревшим.

**Готово, когда:** «Готовится» меняется на «Готов» без ручного перехода между вкладками; повторное открытие не умножает запросы. Push о готовности — отдельное дальнейшее улучшение.

### F04. Восстановление экрана принятого заказа — P1

- [ ] По сохранённому номеру загрузить заказ из репозитория/сервера и показать загрузку, ошибку или результат.

**Готово, когда:** завершение процесса не приводит к возврату в меню только из-за пустого кеша; отсутствие заказа и недоступность сети различаются; запрос выполняется только для подходящей сессии.

### F05. Кофейня и доступные интервалы — P1/P2

- [ ] Показать реальные часы, адрес, состояние «открыто/закрыто» и действие открытия маршрута; заменить фиксированные 350 м корректными данными или убрать расстояние.
- [ ] Предлагать только доступные интервалы самовывоза и объяснять, почему заказать сейчас нельзя.

Для первого шага необязательно запрашивать геолокацию: адрес и расписание уже дают пользу. Достоверные часы и доступность должны иметь определённый источник. Расчёт интервалов использует B09.

**Готово, когда:** статус зависит от выбранной кофейни и времени; пользователь не узнаёт о заведомо недопустимом времени только после закрытия диалога.

### F06. Понятные ошибки оформления — P1/P2

- [ ] При отказе показывать конкретные недоступные товары/опции, изменения цены и способы исправления; отдельно отображать неизвестный исход оформления.

Точные причины требуют расширения серверного ответа. Сохранять выбор пользователя, давать исправить позиции, затем повторять проверку. Связано с B05, B07 и A06.

**Готово, когда:** сообщение объясняет, что исправить; повтор без изменения проблемных данных не является единственным доступным действием.

### F07. Быстрая покупка из избранного — P2

- [ ] Добавить удаление из избранного и добавление в корзину прямо из списка.

Для товара с обязательными настройками открыть выбор либо использовать явно обозначенную сохранённую конфигурацию. Все сердечки используют A03. При обновлении сохранять уже видимый список и показывать ошибку рядом/сообщением; при необходимости добавить обновление свайпом.

**Готово, когда:** простую позицию можно купить без открытия деталей, а сложная не попадает в корзину с неочевидными настройками.

### F08. Продолжение действия после входа — P2

- [ ] Сохранять намерение гостя, например добавить конкретный товар в избранное, и завершать его после успешного входа.

**Готово, когда:** действие выполняется один раз для нужного товара и актуальной сессии; отмена входа его не выполняет; существующий путь «корзина → вход → оформление» сохранён.

### F09. Отмена удаления и активный заказ на главной — P2

- [ ] Добавить восстановление удалённой строки через snackbar.
- [ ] Показывать на главном экране компактный блок активного заказа с переходом в детали.

**Готово, когда:** восстановление учитывает последующие изменения корзины; блок использует общее состояние заказов и исчезает при выходе/завершении по выбранным правилам.

### F10. Восстановление доступа — P2

- [ ] Спроектировать сценарий «Забыли пароль?» с подтверждением владения телефоном и поддержкой сервера.

**Готово, когда:** пользователь может восстановить доступ без создания второго аккаунта; определены ошибки, ограничения повторных запросов и срок действия подтверждения. Одной кнопки без серверного сценария недостаточно.

### F11. Доступность и устойчивость интерфейса — P2

- [ ] Проверить крупный шрифт, длинные названия, клавиатуру, небольшие экраны, TalkBack, контраст, подписи действий и состояния загрузки.
- [ ] При неудачном обновлении сохранять доступное содержимое вместо замены всего экрана ошибкой; дать повторить действие без потери ввода.

**Готово, когда:** основной путь покупки проходим при крупном шрифте и TalkBack; элементы управления доступны; ошибка обновления не уничтожает уже загруженные полезные данные.

### F12. Необязательные возможности — P3

| Возможность | Польза и условие |
|---|---|
| Сохранённая конфигурация напитка | Быстрый повтор «латте L на овсяном»; определить, как она связана с простым избранным |
| Push «Заказ готов» | Не нужно держать экран открытым; требуется серверный канал уведомлений |
| Просмотр меню без сети | Сохранять каталог, показывать актуальность, проверять условия перед оформлением |
| Ссылка на товар | «Поделиться» открывает конкретную позицию; нужен договорённый формат ссылок |
| Онлайн-оплата | Отдельный сценарий с платёжным провайдером, восстановлением результата и сервером |
| Бонусы и промокоды | Сначала определить реальные правила начисления, списания и проверки |
| Состав и аллергены | Добавлять только при достоверных данных; полезно для фильтров большого каталога |
| Оценка заказа | Имеет смысл, если обратная связь действительно обрабатывается кофейней |
| Аватар | Косметическое улучшение; потребуется хранение/загрузка изображения |

## 7. Альтернативная версия с другими библиотеками

### 7.1. Цель и границы — ALT

Сделать отдельно сравнимый вариант **Ktor Client + Navigation 3**, сохранив пользовательские возможности, контракт API и выбранные правила архитектуры. Основной вариант может продолжать использовать Retrofit и Navigation Compose: исправления B01–B10 не требуют их замены.

Предлагаемый способ организации — отдельная ветка, например `codex/alternative-ktor-nav3`, от зафиксированного состояния основного варианта. Не поддерживать два больших почти одинаковых приложения или оба HTTP-клиента в production без явной необходимости. В рамках этого документа ветка не создаётся.

| Область | Основной вариант | Альтернативный вариант |
|---|---|---|
| HTTP | Retrofit + OkHttp | Ktor Client, первоначально с движком OkHttp |
| JSON | kotlinx.serialization | Сохранить kotlinx.serialization через `ContentNegotiation` |
| Навигация | Navigation Compose, `NavController`/`NavHost` | Navigation 3, управляемый стек и `NavDisplay` |
| UI | Compose | Сохранить Compose |
| Сценарии и данные | Предложения раздела 4 | Те же обязанности, независимо от библиотек |
| DI и изображения | `AppContainer`, Coil | Сохранить при первом переносе |
| Хранение | DataStore и выбранное решение для корзины | Не менять одновременно с HTTP и навигацией |

Это учебная/техническая альтернатива. Ускорение, уменьшение APK и улучшение UX нужно измерять, а не считать автоматическим следствием переноса.

### 7.2. Переход на Ktor — ALT-K

- [ ] **K1.** Отделить интерфейс API от Retrofit-аннотаций и технических исключений. При необходимости временно оставить Retrofit-адаптер для общей границы.
- [ ] **K2.** Добавить `KtorCoffeeRunApi` на `HttpClient`, сохранить пути, методы, заголовки, DTO и обработку пустых успешных ответов.
- [ ] **K3.** Настроить `ContentNegotiation` и прежний `CoffeeRunJson`; проверить тела запросов, ответы и язык меню. [Ktor: сериализация](https://ktor.io/docs/client-serialization.html).
- [ ] **K4.** Явно определить обработку HTTP-статусов. В Ktor проверка статуса по умолчанию не включена; использовать согласованную проверку ответа или `expectSuccess` и преобразование исключений. [Ktor: обработка ответов](https://ktor.io/docs/client-response-validation.html).
- [ ] **K5.** Перенести авторизацию, тайм-ауты и debug-логирование. Сохранить исключение входа/регистрации из обработки выхода, защиту нового токена от старого 401 и прохождение отмены. Не логировать токены и пароли.
- [ ] **K6.** Проверить запросы через `MockEngine`; для реального движка оставить необходимые интеграционные проверки через MockWebServer. [Ktor: тестирование](https://ktor.io/docs/client-testing.html).
- [ ] **K7.** Подключить реализацию через `AppContainer`, проверить основной пользовательский путь, затем удалить неиспользуемый Retrofit.

Ktor поддерживает движок OkHttp; поэтому замена API-клиента не требует сразу заменять сетевой транспорт или загрузку изображений Coil. [Ktor: движки](https://ktor.io/docs/client-engines.html).

**Готово, когда:** контрактные проверки проходят для новой реализации; правильно обработаны 204, 400, 401, 404, 409, 5xx, некорректный JSON, тайм-аут и отмена; язык и токен передаются как прежде; `POST /orders` не повторяется автоматически без B05. Версии и совместимость зависимостей выбрать и проверить непосредственно перед переносом.

### 7.3. Переход на Navigation 3 — ALT-N

Navigation 3 ориентирована на Compose и передаёт приложению управление стеком экранов: переходы меняют список его записей. Это требует переноса правил навигации, а не простой замены названий методов. [Android: Navigation 3](https://developer.android.com/guide/navigation/navigation-3).

- [ ] **N1.** Зафиксировать ожидаемые маршруты основного приложения: четыре вкладки, товар, избранное, вход/регистрация, профиль, оформление и заказ.
- [ ] **N2.** Ввести сериализуемые ключи маршрутов, реализующие `NavKey`, и состояние навигации приложения. Предложение: выбранная вкладка, сохраняемые стеки и именованные операции `openProduct`, `openTab`, `afterLogin`, `showPlacedOrder`.
- [ ] **N3.** Заменить `NavHost`/`NavController` на `NavDisplay` и операции над стеками. Экраны сохраняют callbacks и не управляют деталями библиотеки.
- [ ] **N4.** Передавать аргументы ключа в создание ViewModel; обеспечить независимую ViewModel и сохраняемое состояние каждой записи стека, в том числе повторных открытий одного типа экрана.
- [ ] **N5.** Восстанавливать стеки и состояние записей; `rememberNavBackStack` — возможная основа. Восстановление маршрута дополнять восстановлением данных заказа по B04/F04. [Android: сохранение состояния Navigation 3](https://developer.android.com/guide/navigation/navigation-3/save-state).
- [ ] **N6.** Перенести особые правила: возврат из входа в оформление, очистку стека после заказа, выбор вкладок, обновление профиля, выход из аккаунта. Предпочитать общее состояние профиля техническому сигналу предыдущему экрану.
- [ ] **N7.** Проверить жест/кнопку «назад», переход изображения товара и прочие анимации, сохранение состояния вкладок и поведение после завершения процесса.

**Готово, когда:** основные пути дают ожидаемый стек; «назад» не возвращает к уже завершённому оформлению; вкладки сохраняют согласованное поведение; поворот не создаёт новую операцию покупки; восстановление не показывает данные прежней сессии. Решения об отличиях от старой навигации должны быть явными.

### 7.4. Порядок и сравнение вариантов

1. Зафиксировать базовую версию и сценарии проверки; внедрить общие исправления данных либо определить, как переносить их в альтернативу.
2. Изолировать сетевые ошибки и перенести HTTP на Ktor отдельным изменением.
3. Проверить весь сценарий покупки при прежней навигации.
4. Перенести навигацию на Navigation 3 отдельным изменением.
5. Сравнить корректность, объём кода и сложность тестов; при необходимости измерить время сборки, размер APK и восстановление состояния в одинаковых условиях.

Переходы Ktor и Navigation 3 независимы: альтернативу можно остановить после Ktor. Hilt/Koin, Room, многомодульность или MVI не являются обязательной частью этого эксперимента.

## 8. Предлагаемые этапы основной версии

Это порядок для выбора следующих задач, а не календарный график. Отдельная задача может включать архитектурную предпосылку: например, исправление повтора сразу создаёт соответствующий use case.

| Этап | Работы | Проверяемый результат |
|---|---|---|
| 1. Сессия и заказы | B01, B03, B04, A01/A04 в нужной части | Старые ответы не портят новую сессию; список и детали согласованы |
| 2. Сценарий оформления | B05, B06, B09, `PlaceOrderUseCase`, необходимые изменения контракта | Определены исход операции и судьба корзины; время не меняется молча |
| 3. Избранное | B02, A03, соответствующие проверки | Последнее намерение сохраняется, ошибки не откатывают новое действие |
| 4. Повтор и история | B07, B08, B10, `RepeatOrderUseCase`, обновление меню | Повтор использует текущие условия; история сохраняет оплаченный состав |
| 5. Восстановление и удобство | F01–F06 в оставшейся части, F11 | Перезапуск не теряет важные данные; основной путь покупки понятен |
| 6. Быстрые действия | F07–F10, оставшиеся A02/A05/A06 | Меньше повторных действий, понятные ошибки и общий код сценариев |
| 7. Дальнейшее развитие | Выбранные F12, A07/A08, Q03 | Добавляются только возможности с понятной пользой |
| Отдельный эксперимент | ALT-K, затем ALT-N | Сравнимая версия с другим стеком |

Если ближайшая цель — локальное хранение для следующей лабораторной, можно начать с **F01**, заранее определив правила аккаунтов и версии корзины. Если нужна небольшая самостоятельная задача по архитектуре — **B07 + `RepeatOrderUseCase`**. Для снижения риска некорректных данных приоритет сохраняют этапы 1–2.

Работы, требующие нового сервера, можно разделять на клиентскую подготовку и серверную реализацию. Отсутствие серверной поддержки должно оставаться видимым ограничением, а не закрываться демонстрацией на моке.

## 10. Что считать завершением задачи

Перед отметкой пункта нужно проверить его критерий, сохранить существующий основной путь и обновить затронутые тесты/контракт/документацию. Для ошибок с конкурентностью необходим управляемый сценарий задержанных ответов; обычной ручной покупки недостаточно.

Ни один пункт этого документа сам по себе не означает согласие на реализацию всех изменений. Ближайшие задачи выбираются отдельно. При первоначальном составлении документа прикладной код не менялся; последующая реализация отражается в примечаниях о прогрессе и отдельных планах.
